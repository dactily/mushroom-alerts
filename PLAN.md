# mushroom-alerts: уведомления в Telegram о грибах вокруг Valašské Meziříčí

Дата разведки: 2026-09-07. Локации по умолчанию: Valašské Meziříčí (49.4718 N, 17.9711 E) и Valašská Bystřice (49.416 N, 18.106 E, лес приятнее). Набор локаций расширяемый, см. п. 2a.

Статус на 2026-09-08: последовательный рефакторинг завершён локально восемью логическими коммитами поверх исходной реализации. Добавлены явные ошибки источников и расчёта, типизированное качество данных, календарные окна, консервативный суточный стык, архив выпусков с миграциями SQLite, единое представление для `rules`/`brief`/`status`, разделение `derive`/`evaluate`/`render`/эмиссии, биологические признаки и команда `calibration`. Формула API30, порог 25 мм и правила уведомлений не перекалиброваны. Журнал походов `mark`, почасовая склейка и автоматические поправки прогноза отложены. На VPS эта серия ещё не развёрнута.

Все эндпоинты ниже проверены curl-ом 2026-09-07; поправки по итогам реализации внесены в таблицу и помечены в тексте.

Уточнения по станционным данным (проверено на живых данных при реализации этапа 1):

- **Суточный интервал `SRA`.** `DT` — это *начало* интервала: строка `SRA` с `DT = D 06:00Z` — сумма осадков за `[D 06:00Z, D+1 06:00Z)`. Проверено по 10-минутной ленте: 2.3 мм, выпавшие 5.9 между 04:10Z и 06:00Z, ČHMÚ относит к **4.9**. `API30(D)` считается по 30 дням *до* D и `SRA(D)` не использует. Открытые данные Open-Meteo (`precip_mm`) — наоборот, календарный день Europe/Prague; окна пересекаются на 18 ч, при склейке день D кладётся на день D без сдвига (см. п. 5).

## 2. Рекомендуемая архитектура (MVP)

Один синхронный Python CLI на Hermes-сервере. Своего Telegram-бота нет: два задания Hermes запускают `brief` ежедневно в 08:30 и по пятницам в 19:00 Europe/Prague.

Разделение труда: **скрипт считает всё, Hermes только формулирует.** `brief --mode daily|weekend` печатает готовый короткий блок (≈1 КБ): флаг отправки, заголовок, итог, фазу и по 2–3 строки на локацию — все числа и даты уже окончательные. Hermes ничего не пересчитывает, не интерпретирует и ничего не помнит между запусками. Это исключает и ложную трактовку высокого API30 сразу после дождя, и расхождение вердикта между запусками. `brief` без `--mode` остаётся отладочным видом с таблицами.

Контракт для Hermes остаётся как детерминированный запасной вариант (и на нём же держатся тесты): `python -m mushroom_alerts check` печатает в stdout короткий отчёт и завершается кодом
- `0` — ничего нового, молчать;
- `10` — есть положительный сигнал (текст в stdout переслать как есть);
- `1` — ошибка источника/скрипта (Hermes сообщает об ошибке, но не чаще раза в день).

`brief` завершается кодом `0`, кроме случая «упали все источники» или ошибки расчёта (`1`). Частичный отказ источника или одной локации сохраняет полезный бриф и код `0`. Технический traceback остаётся в stderr. `brief` не пишет состояние эмиссий.

Дополнительно `--json` для машинного вида и `status` для вывода текущего среза по запросу («что там с грибами?»; по этому же вопросу Hermes запускает `brief`).

```
mushroom-alerts/
  mushroom_alerts/
    __main__.py           # CLI: check | brief [--mode] | status [--json]
    brief.py              # отладочный вид: все факты и таблицы
    report.py             # готовый человеческий блок + решение отправлять/молчать
    fetch_chmi_map.py     # PNG → уровень 1–5 в точке(ах)
    fetch_chmi_station.py # open data → SRA, API30, T за 30 дней по ближайшим станциям
    fetch_houbymapa.py    # /predikce → ближайшая ячейка на локацию
    fetch_openmeteo.py    # осадки/T на 16 дней вперёд по координатам локации
    api30.py              # формула API30: пересчёт по станции + продление на прогноз
    rules.py              # решение: сигнал есть/нет, текст отчёта, exit code
  locations.yaml          # локации (имя, координаты); выведенные параметры кэшируются в SQLite
  state.sqlite            # история значений + что уже сообщали
  pyproject.toml, Dockerfile (опционально; можно и venv + cron Hermes)
```

Хранить в SQLite каждый ежедневный срез (дата, локация, источник, значение). Это сразу даст историю для валидации (п. 5) и графики в Metabase, который уже стоит на сервере. Антиспам («уже сообщали») и состояние отчётов (таблица `reports`) тоже живут в SQLite, а не в памяти Hermes.

### 2a. Несколько локаций

- пиксель на карте ČHMÚ (по bbox, см. п. 1);
- ближайшая ячейка HoubyMapa (сетка 0.2°, haversine до центров);
- 1–2 ближайшие станции ČHMÚ из `meta1-YYYYMM.json` (haversine), с высотой.

### 2b. Доставка через Hermes, без своего бота

Решение: своего Telegram-бота пока не делаем. У Hermes Agent уже есть cron и Telegram-канал к пользователю, поэтому он работает только транспортом и редактором текста.

Два задания Hermes, независимые друг от друга:
- **ежедневно 08:30 Prague** — `hermes/mushroom_brief.sh` запускает `python -m mushroom_alerts brief --mode daily`;
- **пятница 19:00 Prague** — `hermes/mushroom_weekend.sh` запускает `python -m mushroom_alerts brief --mode weekend`; план на выходные отправляется всегда.

Скрипт печатает в stdout готовый блок: `ОТПРАВЛЯТЬ: да|нет`, `ПРИЧИНА`, `ЗАГОЛОВОК`, `ИТОГ`, `ФАЗА`, по блоку на локацию и `ОГОВОРКИ`. Промпт (`hermes/daily_prompt.txt`, `hermes/friday_prompt.txt`, ≤ 12 строк каждый) говорит ровно две вещи: при `ОТПРАВЛЯТЬ: нет` ответить `[SILENT]`, иначе переписать блок как короткое сообщение в Telegram, сохранив все числа и даты дословно. Hermes не знает ни про окна роста, ни про дождевые эпизоды, ни про пороги.

Состояние живёт в SQLite (таблица `reports`: дата, режим, вердикты по локациям, дата возможной высокой вероятности, доминирующее событие, класс ошибки, версия правил, решение и его причина). Durable notepad и рендер промптов по job ID больше не используются и удалены.

Вопрос «что там с грибами?» — тот же `brief` (без `--mode`, полный вид), ответ сразу, вне правил тишины. Флаг `status --weekly` сохранён как совместимый no-op.

Запасной детерминированный путь без всякой интерпретации остаётся: `python -m mushroom_alerts check`, exit `10` → Hermes пересылает stdout, `0` → молчит, `1` → сообщает об ошибке; контракт не меняется и покрыт тестами.

Hermes v0.20.4 сохраняет результат транспорта в `delivery_outcome`. Приложение не записывает его обратно в SQLite. Запись `signal_emissions` означает только эмиссию `check` в stdout, а строка в `reports` — вычисленный отчёт. Exactly-once не обещается: при ошибке доставки после записи строки состояние уже изменено.

Плюсы: ноль новых токенов и чатов; сообщение человеку читается как фраза; расход токенов вернулся к минимуму — Hermes получает ≈1 КБ вместо ~3 КБ на локацию, и весь риск выдумывания чисел снят, потому что переписывать нечего, кроме готового текста. Минусы: доставка по-прежнему зависит от работоспособности Hermes gateway.

Отдельный Telegram-бот (свой long polling, команды `/add`, геопозиции) отложен; при необходимости добавляется как этап 5 без изменения ядра: ядро уже CLI + SQLite, боту останется только вызывать те же функции и печатать тот же блок.

## 3. Логика уведомлений

Принцип: сообщение человеку только при **переходе состояния**, плюс план на выходные по пятницам в 19:00. Решение принимает скрипт, не LLM.

Правила отправки ежедневного сообщения (`brief --mode daily`) — оба про изменение относительно последнего отчёта с **предыдущей** даты:

1. вердикт по любой локации отличается от прошлого отчёта (в любую сторону);
2. дата возможной высокой вероятности впервые вошла в ближайшие 7 дней, пропала из них или сдвинулась больше чем на 2 дня.

Дополнительно отправка происходит при первом запуске (прошлого отчёта нет) и при смене класса ошибки `error_class` (`none` / `station` / `brief`). Недоступность карты ČHMÚ или HoubyMapa класс не меняет: она попадает только в строку `ОГОВОРКИ`, чтобы замерший второстепенный источник не выглядел новостью. Повтор той же ошибки на следующий день сообщения не даёт. Пока «высокая» держится без изменений, ежедневно не пишем: грибы стоят на месте 5–10 дней, а пятничный план напомнит.

Режим `weekend` отправляется всегда, даже если ничего не изменилось и вердикт «низкая»; если бриф не собрался — одна строка про отсутствие данных.

Повторный запуск того же режима в тот же день идемпотентен: сравнение всегда идёт с отчётом более ранней даты, а строка за сегодня перезаписывается.

Ниже — детерминированные триггеры `rules.decide`. Это контракт команды `check` (exit `10`/`0`/`1`) и запасной путь без интерпретации; отладочный `brief` печатает строкой, какие из них сработали сегодня.

Триггеры (любой из них → exit `10` и текст в stdout):
1. **ČHMÚ**: уровень в точке локации стал ≥ 4, либо вырос на ступень относительно предыдущего сохранённого дня. Уровень читается как majority по окну 5×5 пикселей вокруг точки (растр 2755×1600, ~0.16 км/px, см. п. 1). Карта с пометкой `meta.stale` (не обновлялась > 2 дней) игнорируется: замерший источник не должен выглядеть новостью. Оценивается для каждой локации отдельно.
2. **HoubyMapa**: в ближайшей к локации ячейке `l ≥ 4` или `s ≥ 0.6`, и вчера (предыдущий сохранённый день) этого не было.
3. **Дождь-предвестник** (по ближайшей станции локации): за последние 3 станционных дня (включая сегодняшний предварительный из 10-мин ленты) сумма SRA ≥ 20 мм при средней T 12–22 °C → сообщение «déšť X mm … → okno D+7–D+12», где D — самый мокрый день окна. Все подходящие окна истории рассчитываются заново, перекрывающиеся окна одного дождевого периода объединяются, раздельные периоды сохраняются как отдельные события. Более свежий дождь в фазе ожидания не скрывает старое активное окно. D+7–D+12 является основной фазой, в которой возможен высокий вердикт; D+13–D+21 является остаточной фазой с максимумом «средняя». Второе сообщение — когда основное окно наступило и станционный API30 всё ещё ≥ порога (п. 4).
4. **Прогнозный API30** (своё, этого нет ни у одного источника). Для каждой локации: берём фактические полные суточные SRA станции за последние 30 дней, затем целые модельные дни Open-Meteo и считаем API30 на каждый день вперёд по формуле из п. 5 (`API30(t) = Σ_{j=1..30} SRA(t−j)·0.93^j`). Полный станционный день имеет приоритет. Неполный станционный день показывается как нижняя оценка, но не вытесняет и не складывается с модельным днём. При отсутствии обоих остаётся разрыв. Триггер: прогнозный API30 пересекает порог снизу вверх в день D, сегодня он ниже порога, и вчера такого пересечения в прогнозе не было (или дата D сдвинулась больше чем на 2 дня, или прошлое уведомление старше 14 дней). Дополнительное условие: T прогноза Open-Meteo на день D — средняя в 8–22 °C, ночной минимум > 2 °C; неизвестная температура закрывает триггер.

   **Порог: 25 мм, предварительно.** 25 мм переопределяется переменной окружения `MUSHROOM_API30_THRESHOLD`. Команда `calibration [--json]` уже считает размер выборки, bias и MAE осадков/API30 по локациям и горизонтам 1–3, 4–7, 8–16 дней, но не меняет порог и не корректирует прогноз автоматически. Выпуски хранятся в `forecast_runs`/`forecast_points`, включая текущий день; legacy-таблица `forecasts` остаётся для отката.
5. **Антиспам**: одна и та же новость (ключ сигнала: уровень, идентификатор дождевого события, дата пересечения D) не повторяется в течение недели. Проверка идёт по точному ключу события, поэтому соседнее событие не сбрасывает cooldown предыдущего. Повторный запуск `check` в тот же день печатает то же самое и тот же exit code; readings, forecast runs и emissions при одинаковом входе не дублируются. Сетевые GET и повтор stdout остаются намеренными. Хистерезис «после „сезон открыт“ молчать, пока не упадёт до ≤ 2» решено **не** делать.

Формат сообщения: одна строка на локацию, факты + сработавшие триггеры: «🍄 Valašské Meziříčí: ČHMÚ 3/5, HoubyMapa 3/5 (0.47), stanice API30 20 mm, SRA 3d 0.2 mm, T 14.2 °C · prognóza: API30 ≥ 25 mm od 22.9. (vrchol 35 mm 23.9., déšť 10 mm 22.9.) — orientačně» (реальный вывод 7.9.2026). При exit 10 в текст попадают только локации со сработавшим триггером; `status` печатает все и вместо триггеров даёт сводку прогноза. Недоступный источник добавляет пометку в скобках, например «(HoubyMapa nedostupná)».

## 5. Своя карта / свой индекс — имеет ли смысл

Вывод: **свою карту делать не надо, свой локальный индекс — да, но дёшево.**

- ČHMÚ сам публикует API30 по станции Valmez в открытых данных, так что «строить карту» = повторять ČHMÚ. Формула **воспроизведена точно**: `API30(t) = Σ_{j=1..30} SRA(t−j)·0.93^j`, MAE **0.025 мм** при max 0.05 мм на 341 дне (2025-10-01 … 2026-09-06) — а 0.05 мм это и есть шаг округления публикуемых значений. Подгонка сканированием: минимум ровно на decay 0.930 и окне 30, день `t` в окно не входит (осадки за `t` в 06:00Z ещё не сняты). Прежний вариант из разведки `Σ SRA(t−j)·0.92^(j−1)` даёт MAE 0.655 мм — в 25 раз хуже, он оставлен в коде только как `PLAN_DECAY`/`PLAN_LAG_OFFSET` для сравнения. Из осадков Open-Meteo индекс продлевается на прогноз вперёд (это ровно то, чего нет у ČHMÚ) — триггер 4 в п. 3, этап 1b.
  Стыковка станции и Open-Meteo: день Open-Meteo D кладётся на станционный день D без сдвига (окна `[D 00:00 Prague, D+1 00:00)` и `[D 06:00Z, D+1 06:00Z)` перекрываются на 18 ч); ошибка от этого много меньше систематического перекоса самой модели (п. 6).
- Что ČHMÚ не даёт: локальность по высоте и лесу. Valmez (334 м) и Kateřinice-Ojičná (586 м) — разные осадки и температуры. Собственный индекс = тот же API30, но по 3–4 станциям + порог по температуре, отдельно «низина/Hostýnské vrchy/Vsetínské vrchy».
- Как проверить, что расчёт совпадает с реальностью (это и есть главный открытый вопрос):
  1. Автоматически: сравнивать ежедневно свой индекс с уровнем ČHMÚ и с HoubyMapa — сходимость моделей (SQLite уже накапливает). Отдельно: прогнозный API30, посчитанный N дней назад на сегодня, против фактического API30 станции сегодня — ошибка прогноза по горизонту N.
  2. По людям и по себе — отложено, см. п. 8.

## 6. Риски и ограничения

- `data-provider.chmi.cz/api/data/rizika/houby`, `houbymapa.cz/predikce`, `mapahub.cz/api/skore` — неофициальные эндпоинты, могут поменяться без предупреждения. Скрипт должен падать мягко: источник недоступен → пометка в сообщении, остальные работают. Open data ČHMÚ — единственный гарантированно стабильный источник, на нём держать основной триггер.
- ČHMÚ данные — лицензия CC BY 4.0, для личного бота атрибуция не проблема, но в сообщении можно писать «zdroj ČHMÚ».
- Суточные open data отстают на ~1 день; 10-минутные (`now/`) закрывают сегодняшний дождь, если нужно быстрее.
- Прогноз осадков Open-Meteo на 7+ дней ненадёжен, особенно летние конвективные ливни: сумма может уехать в разы. Поэтому триггер 4 срабатывает один раз на пересечение и не дёргает при сдвиге даты ≤ 2 дня; для дальнего горизонта (>7 дней) пишем «orientačně».
- **Насколько Open-Meteo расходится со станцией (измерено 7.9.2026, 62 дня 2026-07-07 … 2026-09-06, точка Valmez против `0-203-0-11769`)**: суммы **184.6 мм у Open-Meteo против 96.8 мм у станции** — модель примерно в 1.9 раза «мокрее»; MAE по дням 2.90 мм; корреляция по дням всего 0.24, но по 5-дневным блокам 0.82 (конвективные дни сдвинуты на сутки: 28.8 станция 17.2 мм ↔ Open-Meteo 32.5 мм на 29.8). Вывод для `api30.py`: станция главнее везде, где у неё есть значение, а прогнозный хвост читать как ориентир, а не как измерение; порог для прогнозной кривой калибровать отдельно от станционного (см. п. 3, триггер 4).
- Нагрузка на чужие сайты: 1–2 запроса в день на источник, User-Agent с контактом.
- Карта ČHMÚ описывает микоризные грибы (hřib, kozák, liška); для václavky/дрожжевых на дереве модель не работает — это ограничение источника, не бота.

## 7. Что решено не делать

- LLM (Hermes Agent) используется **только для формулировки** ежедневного сообщения и решения `[SILENT]`. Вердикт на сегодня, фаза цикла и прогнозные вердикты по датам детерминированы приложением; Hermes обязан их копировать без повышения. Сбор данных, арифметика, пороги и даты также остаются в скрипте.
- Не растить свою растровую карту и не тянуть радар ČHMÚ (HDF): HoubyMapa уже это делает и отдаёт JSON.
- Не делать своего Telegram-бота и не использовать бизнес-бота: доставку берёт на себя Hermes по cron (см. п. 2b). Отдельный бот — возможный этап 5.

## 8. Отложено: обратная связь от людей и своих походов

Ядро (п. 1–4) работает только на моделях: ČHMÚ, HoubyMapa, станции. Это вероятность условий, не факт наличия грибов. Проверка «есть ли реально» отложена в самый конец, отдельным этапом 5, потому что не влияет на архитектуру: ядро уже CLI + SQLite, сюда добавляются только новый fetcher и одна команда.

### 8a. NaHouby.cz — отчёты грибников

- Источник: HTML `https://www.nahouby.cz/kde-rostou/zlinsky-kraj` (+ `/strana-2`), посты `div#prispevek-NNNNN`, дата `DD. MM. YYYY - HH:MM`. RSS/API нет. ~8 постов/неделя по краю, локации только в тексте.
- Модуль `fetch_nahouby.py`: регулярка по `prispevek-` и дате, дедуп по id в SQLite, парсер держать простым; падение не критично.
- Ключевые слова по локации (радиус ~10 км, руками; потом можно из OSM/Nominatim). Valmez: Valašské Meziříčí, Valmez, Kelč, Zašová, Choryně, Jarcová, Podolí, Branky, Lešná, Loučka, Hostýn, Kelčský Javorník. Bystřice: Valašská Bystřice, Bystřička, Rožnov, Vidče, Střítež, Malá Bystřice, Vsetínské vrchy, Radhošť, Hošťálková, Ratiboř. Слишком широкие слова (Vsetín, Halenkov — 20+ км, матчат региональные посты) не брать или только в дайджест.
- Позитивная лексика (hřib, praváci, kuřátka, košík, plný) → триггер: переслать текст поста и ссылку. Негативная («nic», «sucho») только в дайджест.
- Второй cron днём (14:00) `check --only nahouby` для свежих постов.
- Ретро-проверка: посты доступны постранично, можно выкачать сезоны 2024–2026 и сравнить долю «позитивных» постов за неделю с индексом.
- Срез 5.9.2026: «tak to po pauze začíná — Halenkov».

### 8b. Свои походы — `mark <локация> nasel|nic`

- CLI-команда, пишет в SQLite (дата, локация, результат, опционально комментарий). Через Hermes — обычной фразой в чате.
- За сезон даёт 10–20 точек: достаточно, чтобы подобрать порог своего индекса под местность. Без этого калибровка только по сходимости моделей между собой.
