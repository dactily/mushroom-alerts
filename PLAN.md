# mushroom-alerts: уведомления в Telegram о грибах вокруг Valašské Meziříčí

Дата разведки: 2026-09-07. Локации по умолчанию: Valašské Meziříčí (49.4718 N, 17.9711 E) и Valašská Bystřice (49.416 N, 18.106 E, лес приятнее). Набор локаций расширяемый, см. п. 2a.

Статус на 2026-09-07: реализованы этапы **0** (`7a328dd` — скелет CLI, SQLite, карта ČHMÚ, HoubyMapa), **1** (`85241a9` — станции ČHMÚ) и **1b** (`1c17b7c` — Open-Meteo + `api30.py`), плюс интеграция: `rules.py` (все 4 триггера + антиспам), разводка в `__main__.py`, компактный отчёт. Живой прогон `check` даёт exit 10 по прогнозному API30. Добавлена команда **`brief`** (`mushroom_alerts/brief.py` + `hermes/PROMPT.md`): полный набор фактов для Hermes Agent, который и делает интерпретацию — см. п. 2, 2b, 7. Дальше — этап 2 (`add`/`list`/`del` уже есть, остаётся недельный дайджест и Metabase) и калибровка порога API30 по накопленной SQLite.

Уточнения по станционным данным (проверено на живых данных при реализации этапа 1):

- **Суточный интервал `SRA`.** `DT` — это *начало* интервала: строка `SRA` с `DT = D 06:00Z` — сумма осадков за `[D 06:00Z, D+1 06:00Z)`. Проверено по 10-минутной ленте: 2.3 мм, выпавшие 5.9 между 04:10Z и 06:00Z, ČHMÚ относит к **4.9**. `API30(D)` считается по 30 дням *до* D и `SRA(D)` не использует. Открытые данные Open-Meteo (`precip_mm`) — наоборот, календарный день Europe/Prague; окна пересекаются на 18 ч, при склейке день D кладётся на день D без сдвига (см. п. 5).

## 2. Рекомендуемая архитектура (MVP)

Один Python-скрипт (CLI) на Hermes-сервере. Своего Telegram-бота нет: скрипт запускает **Hermes Agent** по своему cron-у раз в день (08:30 Prague — к этому времени обновлены и ČHMÚ, и HoubyMapa, и открытые данные за позавчера).

Разделение труда: **скрипт собирает данные, Hermes их интерпретирует.** Сырые числа (API30 20 мм, SRA 3d 0.2 мм) человеку ничего не говорят, поэтому основная ежедневная команда теперь `python -m mushroom_alerts brief` — компактный брифинг с фактами (текущие значения, история 14 дней, прогноз на 16 дней, сработавшие триггеры, справка «Как читать»). Hermes читает его и своими словами пишет в Telegram, насколько вероятен рост сейчас и когда станет вероятным (через 3/5/7 дней), предупреждая заранее. Инструкция для cron-задачи Hermes лежит в `hermes/PROMPT.md`. LLM не участвует ни в сборе данных, ни в вычислениях — только в формулировке (см. п. 7).

Контракт для Hermes остаётся как детерминированный запасной вариант (и на нём же держатся тесты): `python -m mushroom_alerts check` печатает в stdout короткий отчёт и завершается кодом
- `0` — ничего нового, молчать;
- `10` — есть положительный сигнал (текст в stdout переслать как есть);
- `1` — ошибка источника/скрипта (Hermes сообщает об ошибке, но не чаще раза в день).

`brief` завершается кодом `0` всегда, кроме случая «упали все источники» (`1`): его читают, а не сравнивают с кодом. Частичный отказ источника нормален — брифинг печатается по остальным, а упавший источник попадает в строку «сбои источников».

Дополнительно `--json` для машинного вида и `status` для вывода текущего среза по запросу («что там с грибами?»; по этому же вопросу Hermes запускает `brief`).

```
mushroom-alerts/
  mushroom_alerts/
    __main__.py           # CLI: check | brief | status [--json]
    brief.py              # брифинг фактов для Hermes (интерпретация — на его стороне)
    fetch_chmi_map.py     # PNG → уровень 1–5 в точке(ах)
    fetch_chmi_station.py # open data → SRA, API30, T за 30 дней по ближайшим станциям
    fetch_houbymapa.py    # /predikce → ближайшая ячейка на локацию
    fetch_openmeteo.py    # осадки/T на 16 дней вперёд по координатам локации
    api30.py              # формула API30: пересчёт по станции + продление на прогноз
    rules.py              # решение: сигнал есть/нет, текст отчёта, exit code
  locations.yaml          # локации (имя, координаты); выведенные параметры кэшируются в SQLite
  state.sqlite            # история значений + что уже сообщали
  pyproject.toml, Dockerfile (опционально; можно и venv + cron Hermes)
```

Хранить в SQLite каждый ежедневный срез (дата, локация, источник, значение). Это сразу даст историю для валидации (п. 5) и графики в Metabase, который уже стоит на сервере. Антиспам («уже сообщали») тоже живёт в SQLite, а не в памяти Hermes.

### 2b. Доставка через Hermes, без своего бота

Решение: своего Telegram-бота пока не делаем. Hermes Agent уже имеет cron и Telegram-канал к пользователю, поэтому:
- Hermes cron раз в день в 08:30 Prague запускает `python -m mushroom_alerts brief` (абсолютный путь к venv, как у других его задач), читает брифинг и сам решает, что и как сказать: вердикт на сегодня (низкая/средняя/высокая), прогноз «станет хорошо через N дней (дата)», ближайший дождь; когда молчать — тоже его решение по правилам из `hermes/PROMPT.md` (изменился вердикт / высокая вероятность сегодня / ожидается в пределах 7 дней; по воскресеньям — дайджест всегда);
- запасной детерминированный путь без интерпретации: `python -m mushroom_alerts check`, exit code `10` → Hermes пересылает stdout в чат; `0` → молчит; `1` → сообщает об ошибке. Этот контракт не меняется и покрыт тестами;
- вопрос «что там с грибами?» — тот же `brief`, ответ сразу, вне правил тишины (второй сниппет промпта);
- дайджест по воскресеньям: пока `brief` + просьба к Hermes подытожить неделю; `status --weekly` (этап 2) остаётся в планах для детерминированного варианта.

Плюсы: ноль новых токенов и чатов, сообщение человеку читается как фраза, а не как строка чисел. Минусы: доставка зависит от работоспособности Hermes gateway; ежедневный запуск теперь тратит заметно больше токенов, чем пересылка одной строки (брифинг ~3 КБ на локацию); формулировку делает LLM, поэтому в промпте прямо запрещено выдумывать числа и велено считать раздел «Как читать» авторитетным.

Отдельный Telegram-бот (свой long polling, команды `/add`, геопозиции) отложен; при необходимости добавляется как этап 5 без изменения ядра: ядро уже CLI + SQLite, боту останется только вызывать те же функции.

## 3. Логика уведомлений

Принцип: положительный результат (exit `10`) только при **переходе состояния**, не при просто хороших значениях, плюс короткий недельный дайджест по воскресеньям вечером.

Триггеры остаются детерминированными и после перехода на `brief`: их считает `rules.decide`, а `brief` только печатает строкой «сработавшие триггеры» те из них, что сработали сегодня (или «нет»). То есть Hermes видит и факты, и то, что о них думает сам скрипт, но правило «сработал триггер» никакой LLM не переопределяет.

Триггеры (любой из них → exit `10` и текст в stdout):
1. **ČHMÚ**: уровень в точке локации стал ≥ 4, либо вырос на ступень относительно предыдущего сохранённого дня. Уровень читается как majority по окну 5×5 пикселей вокруг точки (растр 2755×1600, ~0.16 км/px, см. п. 1). Карта с пометкой `meta.stale` (не обновлялась > 2 дней) игнорируется: замерший источник не должен выглядеть новостью. Оценивается для каждой локации отдельно.
2. **HoubyMapa**: в ближайшей к локации ячейке `l ≥ 4` или `s ≥ 0.6`, и вчера (предыдущий сохранённый день) этого не было.
3. **Дождь-предвестник** (по ближайшей станции локации): за последние 3 станционных дня (включая сегодняшний предварительный из 10-мин ленты) сумма SRA ≥ 20 мм при средней T 12–22 °C → сообщение «déšť X mm … → okno D+7–D+12», где D — самый мокрый день окна. Второе сообщение — когда это окно наступило и станционный API30 всё ещё ≥ порога (п. 4).
4. **Прогнозный API30** (своё, этого нет ни у одного источника). Для каждой локации: берём фактические суточные SRA ближайшей станции ČHMÚ за последние 30 дней, дальше подставляем прогноз осадков Open-Meteo на 16 дней и считаем API30 на каждый день вперёд по формуле из п. 5 (`API30(t) = Σ_{j=1..30} SRA(t−j)·0.93^j`). Стыковка: за дни, где станционный файл ещё не вышел (вчера/сегодня), берём 10-мин данные `now/` (они уже приходят как `sra_mm` с `meta.provisional`) и `past_days` Open-Meteo; станция всегда главнее прогноза. Триггер: прогнозный API30 пересекает порог снизу вверх в день D, сегодня он ниже порога, и вчера такого пересечения в прогнозе не было (или дата D сдвинулась больше чем на 2 дня, или прошлое уведомление старше 14 дней) → «prognóza: API30 ≥ T мм od D (vrchol X мм D2, déšť Y мм D−k)», при D − сегодня > 7 дней добавляется «orientačně». Дополнительное условие: T прогноза Open-Meteo на день D — средняя в 8–22 °C, ночной минимум > 2 °C; неизвестная температура закрывает триггер.

   **Порог: 25 мм, предварительно.** Прежние «40 мм, потому что API30 = 41 мм ↔ ČHMÚ 3/5» — ошибка разведки: 6.9.2026 станция опубликовала API30 = **20.3 мм** (Valmez) и **17.0 мм** (Bystřice) ровно в тот день, когда карта показывала 3/5 обеим. 40 мм не были бы взяты за весь измеренный сезон. 25 мм переопределяется переменной окружения `MUSHROOM_API30_THRESHOLD`. **Калибровка по SQLite ещё не сделана** — накопить уровни карты ČHMÚ и подобрать порог, при котором факт API30 лучше всего разделяет дни с уровнем ≥ 4 и ≤ 3 (п. 5, пункт 1). Скользящий прогноз уже пишется в SQLite (таблица `forecasts`: дата расчёта, локация, D, API30 на D), чтобы измерить ошибку прогноза по горизонту. Триггер 3 остаётся быстрым сигналом по факту дождя; триггер 4 уточняет датой.
5. **Антиспам**: одна и та же новость (ключ сигнала: уровень, дата дождя, дата пересечения D) не повторяется в течение недели; повторный запуск `check` в тот же день печатает то же самое и тот же exit code (идемпотентность важнее молчания). Хистерезис «после „сезон открыт“ молчать, пока не упадёт до ≤ 2» решено **не** делать.

Формат сообщения: одна строка на локацию, факты + сработавшие триггеры: «🍄 Valašské Meziříčí: ČHMÚ 3/5, HoubyMapa 3/5 (0.47), stanice API30 20 mm, SRA 3d 0.2 mm, T 14.2 °C · prognóza: API30 ≥ 25 mm od 22.9. (vrchol 35 mm 23.9., déšť 10 mm 22.9.) — orientačně» (реальный вывод 7.9.2026). При exit 10 в текст попадают только локации со сработавшим триггером; `status` печатает все и вместо триггеров даёт сводку прогноза. Недоступный источник добавляет пометку в скобках, например «(HoubyMapa nedostupná)».

## 5. Своя карта / свой индекс — имеет ли смысл

Вывод: **свою карту делать не надо, свой локальный индекс — да, но дёшево.**

- ČHMÚ сам публикует API30 по станции Valmez в открытых данных, так что «строить карту» = повторять ČHMÚ. Формула **воспроизведена точно**: `API30(t) = Σ_{j=1..30} SRA(t−j)·0.93^j`, MAE **0.025 мм** при max 0.05 мм на 341 дне (2025-10-01 … 2026-09-06) — а 0.05 мм это и есть шаг округления публикуемых значений. Подгонка сканированием: минимум ровно на decay 0.930 и окне 30, день `t` в окно не входит (осадки за `t` в 06:00Z ещё не сняты). Прежний вариант из разведки `Σ SRA(t−j)·0.92^(j−1)` даёт MAE 0.655 мм — в 25 раз хуже, он оставлен в коде только как `PLAN_DECAY`/`PLAN_LAG_OFFSET` для сравнения. Из осадков Open-Meteo индекс продлевается на прогноз вперёд (это ровно то, чего нет у ČHMÚ) — триггер 4 в п. 3, этап 1b.
  Стыковка станции и Open-Meteo: день Open-Meteo D кладётся на станционный день D без сдвига (окна `[D 00:00 Prague, D+1 00:00)` и `[D 06:00Z, D+1 06:00Z)` перекрываются на 18 ч); ошибка от этого много меньше систематического перекоса самой модели (п. 6).
- Что ČHMÚ не даёт: локальность по высоте и лесу. Valmez (334 м) и Kateřinice-Ojičná (586 м) — разные осадки и температуры. Собственный индекс = тот же API30, но по 3–4 станциям + порог по температуре, отдельно «низина/Hostýnské vrchy/Vsetínské vrchy».
- Как проверить, что расчёт совпадает с реальностью (это и есть главный открытый вопрос):
  1. Автоматически: сравнивать ежедневно свой индекс с уровнем ČHMÚ и с HoubyMapa — сходимость моделей (SQLite уже накапливает). Отдельно: прогнозный API30, посчитанный N дней назад на сегодня, против фактического API30 станции сегодня — ошибка прогноза по горизонту N.
  2. По людям и по себе — отложено, см. п. 8.

## 6. Риски и ограничения

- `data-provider.chmi.cz/api/data/rizika/houby`, `houbymapa.cz/predikce`, `mapahub.cz/api/skore` — неофициальные эндпоинты, могут поменяться без предупреждения. Скрипт должен падать мягко: источник недоступен → пометка в сообщении, остальные работают. Open data ČHMÚ — единственный гарантированно стабильный источник, на нём держать основной триггер.
- ČHMÚ данные — лицензия CC BY 4.0, для личного бота атрибуция не проблема, но в сообщении можно писать «zdroj ČHMÚ».
- Суточные open data отстают на ~1 день; 10-минутные (`now/`) закрывают сегодняшний дождь, если нужно быстрее.
- Прогноз осадков Open-Meteo на 7+ дней ненадёжен, особенно летние конвективные ливни: сумма может уехать в разы. Поэтому триггер 4 срабатывает один раз на пересечение и не дёргает при сдвиге даты ≤ 2 дня; для дальнего горизонта (>7 дней) пишем «orientačně».
- **Насколько Open-Meteo расходится со станцией (измерено 7.9.2026, 62 дня 2026-07-07 … 2026-09-06, точка Valmez против `0-203-0-11769`)**: суммы **184.6 мм у Open-Meteo против 96.8 мм у станции** — модель примерно в 1.9 раза «мокрее»; MAE по дням 2.90 мм; корреляция по дням всего 0.24, но по 5-дневным блокам 0.82 (конвективные дни сдвинуты на сутки: 28.8 станция 17.2 мм ↔ Open-Meteo 32.5 мм на 29.8). Вывод для `api30.py`: станция главнее везде, где у неё есть значение, а прогнозный хвост читать как ориентир, а не как измерение; порог для прогнозной кривой калибровать отдельно от станционного (см. п. 3, триггер 4).
- Нагрузка на чужие сайты: 1–2 запроса в день на источник, User-Agent с контактом.
- Карта ČHMÚ описывает микоризные грибы (hřib, kozák, liška); для václavky/дрожжевых на дереве модель не работает — это ограничение источника, не бота.

## 7. Что решено не делать

- LLM (Hermes Agent) используется **только для интерпретации и формулировки** ежедневного сообщения: он читает `brief` и объясняет человеческими словами, насколько вероятен рост сейчас и когда станет вероятным. Ни сбор данных, ни арифметика ему не отдаются: все входы структурные, API30, триггеры, пороги и даты считает скрипт, LLM их только цитирует. Промпт запрещает выдумывать числа и требует держаться раздела «Как читать». Детерминированный путь `check` с exit-кодами сохраняется как запасной и как то, что проверяют тесты.
- Не растить свою растровую карту и не тянуть радар ČHMÚ (HDF): HoubyMapa уже это делает и отдаёт JSON.
- Не делать своего Telegram-бота и не использовать бизнес-бота: доставку берёт на себя Hermes по cron (см. п. 2b). Отдельный бот — возможный этап 5.

## 8. Отложено: обратная связь от людей и своих походов

Ядро (п. 1–4) работает только на моделях: ČHMÚ, HoubyMapa, станции. Это вероятность условий, не факт наличия грибов. Проверка «есть ли реально» отложена в самый конец, отдельным этапом 5, потому что не влияет на архитектуру: ядро уже CLI + SQLite, сюда добавляются только новый fetcher и одна команда.

### 8a. NaHouby.cz — отчёты грибников

- Источник: HTML `https://www.nahouby.cz/kde-rostou/zlinsky-kraj` (+ `/strana-2`), посты `div#prispevek-NNNNN`, дата `DD. MM. YYYY - HH:MM`. RSS/API нет. ~8 постов/неделя по краю, локации только в тексте.
- Модуль `fetch_nahouby.py`: регулярка по `prispevek-` и дате, дедуп по id в SQLite, парсер держать простым; падение не критично.
- Ключевые слова по локации (радиус ~10 км, руками; потом можно из OSM/Nominatim). Valmez: Valašské Meziříčí, Valmez, Kelč, Zašová, Choryně, Jarcová, Podolí, Branky, Lešná, Loučka, Hostýn, Kelčský Javorník. Bystřice: Valašská Bystřice, Bystřička, Rožnov, Vidče, Střítež, Malá Bystřice, Vsetínské vrchy, Radhošť, Hošťálková, Ratiboř. Слишком широкие слова (Vsetín, Halenkov — 20+ км, матчат региональные посты) не брать или только в дайджест.
- Позитивная лексика (hřib, praváci, kuřátka, košík, plný) → триггер: переслать текст поста и ссылку. Негативная («nic», «sucho») только в дайджест.
- Второй cron днём (14:00) `check --only nahouby` для свежих постов.
- Ретро-проверка: посты доступны постранично, можно выкачать сезоны 2024–2026 и сравнить долю «позитивных» постов за неделю с индексом.
- Срез 5.9.2026: «tak to po pauze začíná — Halenkov».

### 8b. Свои походы — `mark <локация> nasel|nic`

- CLI-команда, пишет в SQLite (дата, локация, результат, опционально комментарий). Через Hermes — обычной фразой в чате.
- За сезон даёт 10–20 точек: достаточно, чтобы подобрать порог своего индекса под местность. Без этого калибровка только по сходимости моделей между собой.
